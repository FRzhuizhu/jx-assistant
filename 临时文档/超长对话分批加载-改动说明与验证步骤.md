# 超长对话分批加载与分批渲染 — 改动说明与验证步骤

时间：2026-11-08（编程模式会话）
背景：主对话 3000+ 条消息（全产品最长）前端打开即卡——网络整包（几 MB JSON）+
DOM 全量挂载（一次性全量 markdown parse + 上万节点）。10-18《前端渲染性能分析》
第一阶段（content-visibility/输入路径/流式降频/事件节流）已落地，本次是其中的
「第二阶段」：分批加载+分批渲染。用户口径：**分批 1000 条；往上滑到只剩 500 条
缓冲时取下一批 1000；回到底部 60 秒不上翻就释放上方已加载批次，下次上翻重新加载**。

## 方案选型

- **分批挂载（落地）**：DOM 只增头部前插（已渲染节点永不重建），配合已有
  content-visibility（离屏跳过布局）＝等效轻量虚拟化的收益，且与折叠
  until-found、Ctrl+F beforematch、data-seq 搜索定位、视口锚定、展开记忆
  全兼容。
- 轻量虚拟化（视口窗口化+离屏卸载）：与上述机制全部冲突，改造成本与回归
  风险极高，收益大头 content-visibility 已拿到——不选。

## 改了什么

### 后端 server.go（+server_tail_test.go）

1. `GET /api/sessions/{id}` 支持分页参数（**不传＝全量，旧调用方零影响**）：
   - `?tail=N`：最近 N 条；`?before_seq=S&limit=N`：seq<S 的最近 N 条；
   - **回合边界向前对齐**：窗口起点向前扩到回合起点（含完整回合——若向右缩，
     起点前的残段会被后续批次再次跳过，永远不被渲染；测试覆盖逐批接力并集=全量）；
   - 切点贴着会话开头的 inherit 标记行时并入本批（继承段不拆开）；
   - 响应增加 `older: {count, sys, tools, envBoundary}`：切点前剩余条数 +
     分组基线（切点前最后一条有效 prompt 的 sys/tools + 摘要覆盖边界）。
2. `isTurnStartMsg`：回合起点判定，口径与前端 lastTurnStart 一致（旧库【前缀
   通知/goal_round 不算起点）。
3. go test：`TestSliceMsgWindow*` / `TestIsTurnStartMsg` / `TestHandleGetSessionTail`。

### 前端 web/app-chat.js（+app-right.js / app-left.js / index.html / style.css）

常量：`LOAD_BATCH=1000`、`LOAD_BUFFER=500`、`RELEASE_OLDER_MS=60000`。

1. **初始窗**：`loadSessionInto`/`openSubSession` 请求带 `?tail=1000`；落地记
   `st.older`（剩余条数+基线）与 `st._baseWinBase`（基础窗基线，释放时恢复）。
   旧后端不认参数（全量、无 older 字段）→ 前端安全降级为现状。
2. **顶条**（#load-older/#sub-load-older，消息列上方独立节点）："上面还有 N 条
   更早消息，上翻自动加载"；在途转圈；到底隐藏；点击立即取。
3. **上翻预取** `maybeLoadOlder`：scroll 监听 rAF 节流；采样视口上 1/4 线命中的
   回合碎片（data-seq/data-key）→ seq 索引换算"视口上方剩余条数"＜500 即触发。
   按「条」而非「像素」判缓冲，消息高矮不均时稳定。
4. **前插渲染** `loadOlder`：`?before_seq=窗口首条` 取批 → 分组（带 older 基线；
   已加载的摘要/压缩账本行混入输入归位到批内真实位置）→ fragment
   `insertBefore(col.firstChild)`，旧 DOM 一个不动 → **按锚元素 rect 差精确归位**
   （scrollHeight 在 content-visibility 下是估算值，+=dh 会累积偏差；程序写
   scrollTop 还会抑制原生滚动锚定）→ 前缀复用记账平移（_pfxLen/_pfxNodes）。
   批次含 inherit 标记行（翻到会话最开头）时走一次全量渲染（继承段折块需要
   重建头部，只发生在翻到头）。
5. **到顶释放** `releaseOlder`（60 秒）：贴底跟随态武装计时（armReleaseOlder），
   离底即取消；触发时移除批次节点、msgs 截回基础窗、older 恢复（条数加回 +
   基线恢复 _baseWinBase）、**直接贴新底**。钉住阅读/加载在途不释放。新回合
   开始（用户消息回显）时主动释放（贴底才生效）——赶在前缀判定之前，渲染仍
   走尾部重建快路径，批记账不作废。
6. **reloadMessages 合并**：只重取 `?tail=1000`，已上翻加载的头部（seq<新窗
   首条）原样保留、older 扣减——attached 事件刷新不再反复拉整段历史（主对话
   被事件轰炸时最大的流量来源）。
7. **refreshCurrent stay 化**：事件驱动的就地翻新走 `openSession(id,{stay:true})`
   → 同会话保留分批窗口合并 + 不 jump（钉住/展开记忆/视口全保留）。顺带修复
   "钉住阅读时子对话回报把视口拽到底"。
8. **jumpToMessage 补齐**（app-left.js）：目标 [data-seq] 未命中且 older.count>0
   → 循环 await loadOlder 直到覆盖或到头（guard 20 上限），再定位闪烁——
   搜索命中前 1000 条之外的消息不再静默失败。
9. 批记账（st._batches）在前缀全量重建（编辑重发/切回）时清空；jump 渲染、
   回首页、乐观切换同步作废分批状态。

## 明确没动

- renderMessages 主流程（前缀复用/尾部重建/空态）、SSE 流式、attachRun 接流、
  edited 截断、乐观切换/导航令牌/snapshotStale、折叠与锚定机制本体。
- 后端不带参数的调用（导出、组件轻量接口、mdview 等）行为不变。

## 人工体验要点（建议手机远程再过一轮）

1. 打开 3000+ 条主对话：应秒级出画面（旧版几 MB 整包+全量挂载）；顶部见"上面还有 N 条"。
2. 连续上翻：接近顶部约 500 条时自动加载上一批，衔接处内容不跳（轻微 0.2 屏
   移动属 content-visibility 实际化，滚动中无感）；翻到头顶条消失。
3. 回到底部 60 秒后上方批次自动放掉（DOM/内存回落）；再上翻重新加载，展开记忆还在。
4. 钉住中部阅读时子对话回报/完成事件到达：视口不再被拽到底、展开的折叠段不收起。
5. 侧栏搜索命中很早的消息：自动补齐后定位闪烁。
