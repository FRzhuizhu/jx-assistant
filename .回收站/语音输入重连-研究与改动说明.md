## 二、桌面版（WebView2）为什么完全不能用——已定位

**结论：WebView2 支持 Web Speech，但我们的桌面壳没给麦克风权限。**

| 证据 | 内容 |
| --- | --- |
| 微软官方回复（WebView2Feedback issue #1613） | 提问人问「`webkitSpeechRecognition` 什么时候能在 WebView2 用」，微软成员回复：问题在于**麦克风授权提示在 WebView2 里没弹出来**，runtime 93.0.954.0+ 已修，并验证了示例代码可用 → **接口是有的，卡在权限** |
| 我们的桌面壳只用了一个第三方绑定库 | `go.mod` 里 `github.com/jchv/go-webview2`；库源码 `webview.go` 建控件时**只显式放行了剪贴板**：`SetPermission(CoreWebView2PermissionKindClipboardRead, Allow)`，其余权限（含麦克风）保持「默认」 |
| 未放行的权限按「默认」处理 | 库的 `PermissionRequested` 回调对没有登记的权限写回 `PermissionStateDefault`；桌面壳里既弹不出可靠的授权气泡，语音输入就会以 `not-allowed` 直接失败 |

这正好解释「Edge 浏览器里勉强能用、换成桌面版就完全没法用」。

**已修（`desktop_windows.go`）**：创建主 WebView2 控件（＝主环境，只在这一次调用里建）之前，把「自动接受媒体权限」开关并进已有的 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`，创建完立刻还原：

```go
const autoGrantMic = "--use-fake-ui-for-media-stream"
prevArgs, hadArgs := os.LookupEnv(webView2ArgsEnv)
if !strings.Contains(prevArgs, autoGrantMic) {
	_ = os.Setenv(webView2ArgsEnv, strings.TrimSpace(prevArgs+" "+autoGrantMic))
}
w := webview2.NewWithOptions(...)
// 立即还原（含用户已设过的参数）
```

效果：**桌面端一启动就带着麦克风权限，整个生命周期一次都不问、也不用用户点授权**，下次启动同样如此——比「首次启动问一次」更省事。右栏浏览器面板用的是**另一个环境**且是惰性创建的，不会被带上这个开关（不给面板里的任意网站自动放行麦克风/摄像头）；Windows 系统级麦克风开关（设置 → 隐私 → 麦克风）仍是最终闸门，**如果那个总开关是关的，谁也救不了**，页面上会提示去打开。

如果以后想要「首次启动弹一次我们自己的授权框、记下来」，需要给绑定库打一个本地补丁（fork + `replace`，显式 `SetPermission(Microphone, Allow)`）＋一个自绘弹窗；当前这版不需要。

**另外两个备选（如果 WebView2 的云端识别仍不理想）**：
1. 你机器上已经装了 Windows 自带的中文离线识别器（`MS-2052-110-WINMO-DNN`，zh-CN Embedded DNN）——后端可以直接驱动它，离线、不用 key；
2. 云端 ASR（见 §四）。

## 三、谁在发请求（前端还是后端）

**结论：前端（浏览器）在发。** 页面直接用 Edge 内置的 Web Speech API，音频由浏览器直接送到微软云端识别服务，**我们的 Go 后端一点关系都没有**。

| 证据 | 位置 |
| --- | --- |
| 只有 `window.SpeechRecognition \|\| window.webkitSpeechRecognition` 与 `rec.start()/stop()`，没有一行 `fetch`/WebSocket | `web/app-chat.js` 语音输入段 |
| Edge 里的 `webkitSpeechRecognition` 是微软自家实现（与 Chrome 用的 Google 服务不是一套） | 同上 → 「微软浏览器的语音输入接口」本身就是微软云端识别，链路里天然有一段公网 |
| 后端没有任何语音路由（只有 `/polish` 润色文字、`voice-active` 听写状态，都不碰音频） | `adapter_dsh_speech.go` |

这也解释了为什么「首次连接慢」：每次新开一个识别会话都要跟云端服务建链，第一次最慢，后续会复用/走热路径。

## 四、本轮改动清单

`web/app-chat.js`（主对话区与右栏子对话共用同一套逻辑，两个按钮各一份状态）：

1. **连接态**：点击 → 转圈（不开始说话）→ `onstart` 才变蓝；连接中再点一次 = 取消。
2. **连接超时 5 秒**（`VOICE_CONNECT_TIMEOUT`）：到点没连上才判这次失败；重试等待 400/800/1200ms，共 3 次（`VOICE_MAX_RETRY`）；3 次都失败 → 浮层报错「网络不稳定」。
3. **录音态掉线**：`onend`（引擎自行收尾）、`onerror`（`network`/`no-speech`/`aborted`）同样退避重试；`not-allowed`（未授权）、`audio-capture`（无麦克风）直接收场不瞎重试。只要有一次文字进来，重试预算清零（长听写不会被「引擎每几十秒断一次」误判）。
4. **灰字暂定层**：未定稿转写显示为灰字（叠层、不吃点击、不进 value）；静置 2.5 秒落成黑色正文；断线/按停/超时时把已有灰字立即落定；引擎重置结果列表时先落定已有内容；同一句被重报时按前缀剥离只补新增部分（中文之间不插空格）。
5. **时长上限 + 倒计时**：240 秒，最后 9 秒出徽标（换数字弹一下）。
6. **按停**：再点麦克风 = 结束听写，先给引擎 1.2 秒把最后一句吐完再收尾。

`web/style.css`：转圈动画、灰字层、倒计时徽标、浮层提示的样式；灰字在场时隐掉 placeholder。

## 五、断线补录（还差你定一件事）

「中途断开时把录音留着，等连上了再转文字」需要**一个识别服务来转写录音**，而后端目前没有任何语音接口：

| 路线 | 识别来源 | 需要什么 | 特点 |
| --- | --- | --- | --- |
| 后端 + 云端 ASR | OpenAI 兼容的 `/audio/transcriptions`（老插件就是这条路）或 Azure Speech | 一个 key（按时长计费） | 准、稳，不占本机 |
| 后端 + 本机离线模型 | SenseVoice / Whisper（技能运行时里已有 onnxruntime） | 下模型（几百 MB）、吃 CPU | 免费离线，首次装配慢 |

你告诉我走哪条（或你手上哪家的语音 key 能用），我就在后端加最小转写接口 + 前端把断线录音缓存对上去。
