## 1. 改前：这个顺序是在哪里、怎么实现的

**结论：完全在前端、由 `renderSessionList()` 里一个 Map 的插入顺序决定；后端不参与目录排序。**

分组渲染：`web/app-left.js:711` 的 `renderSessionList()`，「按工作区」分支（改动前为 `web/app-left.js:763-773`，git HEAD 版本）：

`Map` 是插入有序的，所以**渲染顺序 = `knownWorkspaces()` 的顺序**，而它跟时间完全无关 → 这就是「各个工作目录之间的顺序始终固定」的根源（手动加过的工作区永远在前、默认工作区紧随其后，之后才按会话出现的先后）。

`knownWorkspaces()` 的定义在 `web/app-core.js:403-408`：

```js
function knownWorkspaces() {
  const set = new Set(lsGet('jx.wslist', []));          // 手动「添加工作目录」登记的，localStorage jx.wslist
  if (state.defaultWs) set.add(state.defaultWs);        // 默认工作区（配置里的 workspace）
```

数据来源：`server.go:1032 handleListSessions` → `store.go:620 Store.List()`：


即 `/api/sessions` 一次返回**全部会话**、按 `updated_at` 倒序。旧代码只把这个顺序当作「目录第一次出现的先后」用了一次——目录一旦出现（或进过 `jx.wslist`），位置就永久固定，之后再怎么活动都不动。**没有任何后端接口/字段承载目录顺序**，所以本次改动不需要动 Go 代码。

## 2. 改后：规则与实现

### 2.1 新增：排序键 + 顺序快照（`web/app-left.js:709-753`）

```js
/* ---------- 工作区分组顺序：本次启动只算一次，运行期不重排 ----------
   分组（工作目录）之间的顺序按「该目录里最新的那一个会话的时间」降序……
   只在软件启动时算一次：第一份全量会话列表（/api/sessions 一次返回全部会话）到达时
   算出顺序快照 wsOrderSnapshot 存起来…… */
function sessionSortStamp(s) {                 // 709-727 行区段内
  for (const raw of [s.updatedAt, s.createdAt]) {
    const t = new Date(String(raw || '').replace(' ', 'T')).getTime();
    if (!isNaN(t)) return t;
  }
  return 0;
}

function sessionCountsForWsOrder(s) {          // 734-736
  return s.mode !== 'assistant' && !s.archived;
}

let wsOrderSnapshot = null;                    // 738：目录顺序快照（ws 数组，最新会话降序）

function snapshotWsOrder() {                   // 740-753
  const newest = new Map();                    // ws -> 该目录最新会话的时间戳（毫秒），0 = 还没有会话
  for (const ws of knownWorkspaces()) newest.set(ws, 0);
  (state.sessions || []).forEach((s) => {
    if (!sessionCountsForWsOrder(s)) return;
    const ws = wsOf(s);
    const t = sessionSortStamp(s);
    if (!newest.has(ws) || t > newest.get(ws)) newest.set(ws, t);
  });
  return [...newest.keys()].sort((a, b) => newest.get(b) - newest.get(a));
}
```

**为什么这么放、这么写：**

1. **尺子要和用户看到的一致**：左侧栏默认排序（后端 `ORDER BY updated_at DESC`）与「时间线」视图分带用的都是 `updatedAt`；目录顺序用同一把尺子，才不会出现「某目录里最新的对话比上面那个目录的对话还新，目录却排在后面」。
2. **放在前端、只改这一处**：分组的可见集合（顶层、非 assistant、未归档）本来就由前端 `visible` 过滤定义（`web/app-left.js`），目录顺序与会话列表同源；不动 Go、不加接口，改动面最小，也不影响别人正在改的后端文件。
3. **必须用「快照」而不是「每次渲染都排一遍」**：`renderSessionList()` 在运行期被很多路径调用（切换会话的乐观切换 `applySessionChrome`、SSE 的 `done/report_ready/session_updated`、新建会话、标为未读、回收站操作…）。如果每次渲染都按当时数据排序，发一条消息目录就会跳，正是需求要避免的。

## 3. 「只在启动时算一次」是怎么做到的

| 问题 | 答案 |
| --- | --- |
| 在哪个时机算 | 第一份**全量**会话列表到达时：`loadSessionsNow()` 拿到 `/api/sessions` 之后、**第一次 `renderSessionList()` 之前**（`web/app-left.js:706`）。 |
| 结果存在哪里 | 模块级变量 `let wsOrderSnapshot = null;`（`web/app-left.js:738`），值 = 目录路径数组，已按最新会话时间降序。 |
| 如何避免运行期被动重排 | ① 冻结只发生在 `if (!wsOrderSnapshot) … = snapshotWsOrder()` 这一句里——全文件 `snapshotWsOrder()` **只有 1 个调用点**、`wsOrderSnapshot=` **只有 2 处赋值**（声明 + 这一处冻结），静态检查见 5.1；② `renderSessionList()` 只**读**快照摆位（824-828 行），运行期任何刷新都不重算；③ 快照里没有的目录（运行期手动加的工作区、会话落在新目录）不参与重排，一律追加末尾；④ 会话列表更新 / 新建会话 / 收到消息 / 归档 / 重跑，最终都只是"再来一次 `loadSessionsNow()`"，快照已存在 → 顺序不动。 |
| 启动时会先按旧顺序闪一下吗 | 不会。`web/app-left.js:809-812`：快照还没算出来时 `renderSessionList()` 直接 `return`（一个分组都不画）。首屏本来就没有分组，数据到了和顺序**一起首绘**。 |
| 什么时候会重新算 | 下次启动软件（界面重新加载，`wsOrderSnapshot` 重新从 `null` 开始）。页面刷新 / 重开界面等价于"重新打开界面"，也会重算一次——这是有意的，与"重启软件"语义一致。 |

## 4. 边界问题逐条回答

1. **用哪个时间字段**：会话的 `updatedAt`（最后活动时间），缺失或异常时退回 `createdAt`，两者都不可用记 `0`。
   理由：与 /api/sessions 的排序（`updated_at DESC`）、左侧栏默认排序、时间线视图分带同源；`updatedAt` 表达的是"这个对话最近一次有动静"，正是"最新会话"该有的含义。
   实测判据：种子里 `A-新会话` 的 `createdAt = 2026-09-29 02:40`（全库最新时间戳），它所在目录 A 仍按 `updatedAt=2026-09-28 22:00` 排在第 3 —— 证明用的是 `updatedAt`。
2. **子对话 / 派生子任务是否计入**：**计入**。依据：`dispatch_sub` 建子会话时继承父会话的工作目录（`assistant.go` 中 `ws := t.workspace()`，`sub := &SessionMeta{… Workspace: ws, ParentID: t.sess.ID …}`），子会话就是这个目录里真实发生过的活动；实测库里 2/2 个子会话与父会话同目录。因此"该目录下所有会话"= 含子会话。（`aux` 辅助对话若挂在某会话下，按子会话同样处理。）
   **不计入的两类**：① 数字助理主对话（`mode === 'assistant'`）——它是全局总控，`workspace` 为空会折进默认工作区，它并不隶属任何分组，计它等于让默认工作区凭一个列表里看不见的会话长期占顶；② 已归档会话——用户已把它移出视线，同理不计。
   实测判据：种子数据的"最新"正是这两类（主对话 `02:00`、E-已归档 `01:30`，都比 B 的 `01:00` 新），实际它们既没登顶、也没让自己的目录靠前。
3. **没有任何会话的工作目录**：排最后（排序键 0）。它们彼此之间的相对顺序**严格等于改动前的顺序**（先按 `knownWorkspaces()` 铺一遍 0 键、再用会话时间覆盖，`Array#sort` 稳定）→ 手动「添加工作目录」登记的在前、默认工作区随后。实测：`[B, E2, E1, D]`（E2/E1 是手动添加，D 是默认工作区）。
4. **时间戳缺失 / 异常**：`''`、`undefined`、非法字符串（如 `'not-a-date'`、`'2026-13-45 99:99:99'`）一律记 `0`，不抛异常、不产生 NaN 参与比较；与空目录同档，沉到最后，且不影响别的目录。
5. **启动时数据是否已加载完 / 有没有时序问题**：`/api/sessions` 一次返回全部会话（`store.go List()` 单条 SQL），不存在"只加载一半就排序"；且快照算完才允许首绘（第 3 节的守卫）。实测：启动后的顺序与库内数据完全对得上，且运行期反复刷新不会变化。
6. **左侧栏当前选中的会话会不会被排序影响**：不会。改动只决定"分组（`ws-group`）之间的先后"；组内会话条目仍是原样 `for (const s of items) list.appendChild(sessionItem(s));`（调用点未动），选中态来自 `state.cur → .active` 类，与顺序无关。运行期实测：选中 D 目录里那个会话、并通过它发消息，D 仍停在原来的位置。
